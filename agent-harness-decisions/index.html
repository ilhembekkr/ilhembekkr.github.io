Agent harnesses: six engineering decisions, read from DeepSeek's Super-agent design

Most agent architecture gets decided by what sounds impressive. DeepSeek's Harness team published the reasoning behind theirs — the constraint they hit each time, the obvious fix they rejected, and what the choice cost them. Six decisions, and the skill that's left when you've forgotten the details.

Ilhem Bekkar
Agentic AI & Optimization Engineer @ Omundu × Université Claude Bernard Lyon 1
November 3, 2026 · ~15 min read · Case study

What is an agent harness?

The harness is everything around the model. The loop that decides when to call it. The tools it can reach. What enters its context and what gets dropped. How work starts, stops and resumes. Who is allowed to approve what. The model writes the code; the harness decides which code gets written, when, and whether a human had to sit there while it happened. Two teams running the same model can end up with completely different systems, and the difference is almost always the harness.

On October 31, 2026, the DeepSeek Harness team published a design document for one of these — "Exploring Super-agent Design", in Chinese — together with a prototype, dsh-superagent-prototype: MIT-licensed, and explicitly a research artifact rather than a product. This article is not about the prototype. It is about the reasoning in the document. Full source list in §10.

1. The hype answer and the engineered answer

Give two people the same problem — "our agent system is too slow" — and watch what they reach for.

The first reaches for the thing that looks like progress. A bigger model. More agents, running in parallel. A framework with orchestration in the description. The move is always additive, and it always lands on the component that was already the most impressive part of the system.

The second asks a duller question: what is actually limiting this? Not what feels slow — what is binding. Then they go look at where that constraint sits. More often than not the fix turns out to be removing something rather than adding it, and it is rarely the part anyone wanted to talk about.

That is the whole difference, and it isn't about intelligence or seniority. It's about which question you ask first. The trouble is that the first habit is easy to copy and the second one is usually invisible — you see the architecture a team shipped, not the four options they threw away getting there.

Which is why DeepSeek's document is worth reading closely. It makes the second habit visible six times in a row. Each time, the obvious answer was available and cheap. Each time they went the other way. And each time they wrote down what it cost them, which is the part almost nobody publishes.

What follows is those six decisions. For each one: the situation, the answer most people reach for, what they did instead, what it cost — and the skill that survives after you've forgotten everything about DeepSeek.

2. The constraint nobody measures

The situation. You can run as many coding agents as you're willing to pay for. In practice people run three, maybe five. Past that, throughput goes down rather than up — and not because any machine is saturated.

The reason is that each session needs a human to read it. Sessions don't share context, so the person is the only thing connecting them. Five agents means five transcripts, five sets of decisions to follow, five places where work can quietly stall while looking busy. The developer stops being a developer and becomes the integration layer.

The hype answer. Run more agents in parallel, and build a dashboard so you can see all of them at once.

A dashboard showing five sessions isn't a fix. It's the same load delivered faster.

What they did. They named the constraint — roughly three to five concurrent sessions per person — and made it the quantity the system optimises. Not task success rate. Not token spend. Attention.

Everything downstream follows from that. One resident coordinator you talk to, instead of N sessions you address individually. Agents that stay silent unless they have something that genuinely needs a human. A dashboard that lists only the items requiring a decision, rather than everything in flight. The stated goal, in the prototype's own design philosophy document: take as little human attention as possible, and give as much value as possible.

What it cost. You stop seeing what the system is doing most of the time. A system designed never to interrupt you is also a system you can't glance at. When something does go wrong, you aren't catching it mid-flight — you're reconstructing it afterwards from logs, which is a different and slower skill.

The skill

The binding constraint is often the one with no metric attached. Compute, latency and token spend are instrumented by default, so they win every argument. Human attention isn't instrumented at all, so it loses — even when it's the thing actually capping throughput. Before optimising anything, ask what runs out first, then ask whether you're measuring it.

3. The component that talks must not do the work

The situation. Something has to receive messages from people and decide what happens next. The obvious shape is that this something is also your best agent: it reads the request, writes the code, and replies. One capable thing doing everything.

That shape breaks the moment it's busy. While your coordinator is running a test suite, nobody can reach it. New requests queue behind work that has nothing to do with them.

The hype answer. Make the coordinator the strongest model you have, with every tool attached, because it's the brain of the system.

What they did. They split the system by responsiveness requirement rather than by capability.

The Router is resident. It receives every human message from every channel, decides what should happen, holds state across tasks, and sends the replies. It runs a lighter model, and may not have shell access at all.

Workers are disposable. One per task, each with isolated context, the full execution toolset, and the strongest model. They never speak to a user. They report to the Router, and the Router answers on their behalf.

The important part is the yellow strip at the bottom of that diagram: the Router never breaks a task into steps. It manages the relationship between tasks — recognising that a chat thread from Tuesday and a pull request comment today are the same piece of work — and nothing inside any one of them. That is deliberately a smaller job than a manager agent does. The smaller the job, the easier it is to keep the Router fast.

It's a real divergence from how the better-known harnesses do it. In Claude Code's agent teams, the lead both decomposes the work and coordinates it, and the lead is a session — one team per session, lead fixed for its lifetime, gone when the session ends. Codex has no resident coordinator between triggers at all — each GitHub event starts its own task. DeepSeek's Router is a long-lived process that outlives any individual task, which is exactly what lets it connect two events that arrived a day apart.

What it cost. An extra hop on every exchange, and a Router that cannot verify what a Worker claims it did — it only has the report. Any real check on work quality has to live somewhere else, which is part of why they ended up needing a separate watchdog process.

The skill

Split systems by what must stay responsive, not by what is most capable. The part that answers humans and the part that does heavy work have opposite requirements. One component serving both will always sacrifice the first one, and it will do it exactly when you're under load and need it most.

4. Don't let the model decide what to look at

The situation. Once the agent listens to group chat, email, CI output and PR comments, the input is a firehose and almost all of it is irrelevant. A few hundred messages might contain twenty real requests.

The hype answer. Let the model read everything and judge. It understands context — that's the entire point of using one.

Correct, and unaffordable. Every event becomes an inference call. Cost now scales with how chatty the team is rather than with how much work there is, and latency rises with the volume of the busiest channel.

What they did. Two stages, cheapest first.

First a programmatic filter: source, group, allowlist. Ordinary code, no model, no cost. Only what survives reaches an LLM, which judges the remaining candidates against a written policy — is this a request, is it addressed to us, does a team rule permit acting on it.

The policy is explicit rather than vibes. In the prototype's docs, accept modes are off, observe (the default) and auto. An explicit request must come from an allowlisted person, and bots cannot make one. Anything merely inferred needs a matching written rule. And each accepted item records the policy version it was accepted under, so six months later you can answer why the system thought it was allowed to do that.

What it cost. The cheap stage is silent. Anything it drops is dropped without a model ever seeing it, and nobody is told. A misconfigured allowlist and an idle system look identical from the outside.

The skill

Put the cheap filter in front of the expensive one. This is unremarkable in any other kind of system and routinely skipped in agent systems, where the model gets treated as the first line of defence rather than the last. Deciding what deserves attention is work that code does better, cheaper and more predictably than inference.

5. When something is a bottleneck, take it out of the path

The situation. The Router sees everything, so everything waits on it. A follow-up comment on a pull request that a Worker is already handling still goes to the Router, which has to work out what it is and route it. As volume rises, one component gates the whole system.

The hype answer. Make the Router faster. Stronger model, more instances, shard it by repository.

What they did. They asked whether the Router needed to be in that path at all, and concluded it didn't.

Related events form a Thread: the same pull request, the same chat topic, the same email chain. The first event in a Thread creates a Worker, and that Worker subscribes to the Thread. Every later event goes straight to it. The Router isn't consulted, because there is nothing left for it to decide — ownership was settled when the first event arrived.

What makes this a good decision rather than a lucky one is that they measured what the shortcut was worth by turning it off. Completion time barely moved. Router decisions rose about 30%, and cache-read tokens went from 23.2M to 31.8M. So the honest claim is narrow and specific: the direct path saves coordination work and money, not latency. Plenty of teams would have shipped the same mechanism and claimed the speedup.

What it cost. Subscriptions are many-to-many. Two Workers touching the same pull request now see each other's events, so the context isolation that justified separate Workers in the first place is partly given up — at exactly the moment two agents are most likely to collide.

The skill

Before optimising a bottleneck, ask whether the work needs to pass through it at all. A component is only a bottleneck for traffic it genuinely has to handle. Routing that was decided once does not need deciding again — and removing a hop is cheaper and more reliable than making it fast.

6. Measure the arrival rate before you scale anything

The situation. A single resident Router is a single point of contention, and every architecture review asks the same question: what happens at ten times the load?

The hype answer. Shard it now. Partition by repository, run a Router per team, build the coordination layer while you're in there. Nobody has ever been criticised for designing for scale.

What they did. They measured first — a real Router model with mock Workers, raising the event rate from about 1 to about 40 triggers per minute.

What they found is the reason measuring was worth it. Events arriving while the Router is mid-inference don't pile up as separate calls; they get injected together into the next one. So as load rises, the average batch grows — 1.0 to 2.8 — and the amortised cost of a decision falls, from 6.4 seconds to 1.6. Individual requests got slower (2.5s to 3.9s), but each unit of useful work got cheaper.

A component that becomes more efficient under load is not the component to shard. They concluded one Router suffices at current scale, and didn't build the partitioning layer.

What it cost. Batching trades per-request latency for throughput, so one urgent request is slower under load than it would be alone. And the result holds at roughly 40 events per minute against mock Workers. It says nothing about 400, and they don't claim it does.

The skill

Scaling decisions need an observed arrival rate, not an imagined one. "What if it's ten times bigger" is a question, not a requirement. Measure the curve before you build for a point on it — because some components get better under load, and sharding those is pure cost paid against a problem you don't have.

7. Stop fitting context — address it instead

The situation. An agent that runs for days accumulates far more potentially relevant material than fits in a context window. Every harness hits this, and most hit it on day one.

The hype answer. Get a bigger window, or summarise aggressively and move on.

Both discard information, and neither tells you what was discarded. Summarisation in particular fails silently and confidently: you can't tell the difference between a fact that was never relevant and one that got compressed away two hours ago.

What they did. Two mechanisms, and both are borrowed instincts rather than new ideas.

Inline and spill. Likely-needed content goes into context directly. Content over budget is truncated and replaced with a pointer to the full thing. Nothing is silently dropped — it is moved somewhere and left addressable.

Chain of recall. Triggers, Threads and Workers all carry unique IDs, and every object the model recalls includes the IDs of objects related to it. The model starts from what it has and walks, one hop at a time, to what it needs — rather than being handed everything up front and asked to find the relevant part.

That is an index, and the instinct behind it is a database instinct: don't load the table, load a row and follow its foreign keys. Nothing here required anyone to think about language models at all.

What it cost. Hops are round trips, and every hop is a chance for the model to not bother taking it. Retrieval stops being a guarantee the harness provides and becomes a decision the model makes. Spill makes a loss recoverable; it doesn't make it impossible.

The skill

Replace carrying with addressing. When the data doesn't fit, the first question isn't how to compress it — it's whether the consumer can fetch it on demand. That means giving things stable IDs and making relationships traversable, which is work you have to do before you need it, and which no amount of context window will do for you.

8. What they didn't solve

The most credible section of the document is the one listing what doesn't work.

Workers run commands with no approval step, as the operator's own OS user. The project's docs state that the blocked-command list is "defaults, not a security boundary" — an unusually plain sentence to publish about your own software. Auto-merge is off by default, and when enabled under the default instructions it is limited to approved pull requests under 200 changed lines, with the agent never enabling it as its own account.

Then the one they state and don't answer. If the cloud loop is compromised — by a breach, or by prompt injection — every connected machine goes with it. And there is still no mechanism for an agent to use a credential without that credential entering model context.

That is an open security hole, written down, in the launch material.

It's worth sitting with why that's a good sign rather than a bad one. A document listing only what works is a sales document, and the reader can't tell whether the gaps are absent or simply unexamined. A document that names its own unsolved problem tells you the team went looking for them. The security section is the part of this release I'd trust most, precisely because it's the part that admits the least.

The skill

Ship the honest limitations alongside the work. An unnamed limitation doesn't disappear — it waits to be discovered by someone who trusted you. Writing it down costs a paragraph, and it's the fastest signal a reader has that you actually understood the system you built.

About the evidence

Every number in this article is DeepSeek's own, from a synthetic benchmark: roughly 300 messages and 20 real requests per run, five runs per setup, with the coding step replaced by a timed stub. It measures scheduling, not code quality. The only baseline was a single session with a subagent tool — not a tuned orchestrator, and not Claude Code or Codex. No third party has reproduced any of it.

Read the measurements as a team instrumenting its own system, which is what they are. The reasoning stands on its own either way, and the reasoning is the point. Sources for every figure are in §10.

Look back at that table and notice what isn't in it. Not one of those six skills is about agents.

Separate what must stay responsive. Cheap filter before the expensive one. Take the bottleneck out of the path. Measure before you scale. Address instead of carry. Publish your limitations. Every one is ordinary distributed-systems practice, the kind of thing that has been true since well before anyone deployed a language model.

So the reason this document reads as unusual isn't that agent engineering demanded new ideas. It's that most agent engineering hasn't started borrowing the old ones yet. The field is young enough that the impressive-sounding answer is still available in every conversation, and still wrong in the same, predictable, borrowable ways.

That's the opportunity, and it's a fairly comfortable one. You don't need to invent anything. You need to ask what's actually binding, resist the first answer, and write down what your choice cost you.

11. Frequently asked questions

What is dsh-superagent?

An MIT-licensed research prototype published by DeepSeek's Harness team on October 31, 2026, alongside a design document called "Exploring Super-agent Design." It is a proactive coding agent for a single GitHub repository, optionally connected to a team chat tool. DeepSeek states clearly that it is not an official product, that much of the code was agent-written, and that it differs from their internal version. Several mechanisms described in the document are not implemented in the prototype at all.

How is a Router different from an orchestrator or lead agent?

An orchestrator decomposes one task into steps and coordinates them. The Router does not decompose anything. It manages the relationship between tasks — which Worker owns which thread, and whether two events belong to the same piece of work — and leaves everything inside a task to the Worker. Keeping that job small is what lets it run a lighter model and stay responsive (§3).

Is any of this new compared to Claude Code or Codex?

The primitives aren't. Context-isolated workers, parallel sessions, agents messaging each other and event triggers from GitHub all already exist in both. What's different is the scheduling layer on top: a coordinator that is resident and holds state across tasks rather than dying with a session, admission control over a mixed stream of chat, email and CI events, and routing by thread ownership. Those three together are the contribution.

Why treat human attention as the constraint?

Because in practice it's what runs out first. A developer can follow roughly three to five agent sessions before throughput falls, and sessions don't share context, so the human is the only thing connecting them. Compute and tokens are instrumented and attention isn't, which is exactly why it loses arguments it should win (§2).

What can I actually adopt from this?

The two-stage trigger filter and thread-based routing are both portable to any harness in an afternoon, and both pay for themselves in tokens. Spill-to-pointer plus stable IDs takes longer because it's an indexing decision you have to make before you need it. The attention framing costs nothing and changes what you measure, which is usually where the real change starts.

Should I run the prototype?

Not on anything you care about, and that's DeepSeek's own position. Workers execute commands without approval as your OS user, the blocked-command list is explicitly described as a default rather than a security boundary, and the credential-isolation problem is unsolved. Read the design document; treat the code as a reference implementation rather than something to deploy.
